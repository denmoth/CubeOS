# 12. Права, безопасность, возможности

## Модель угроз

Защищаем от **не-админов** и недобросовестных приложений. Админы считаются доверенными. Шифрование данных и защита от того, кто попал в CraftOS или взломал администратора ресурса, описаны в [14-data-protection.md](14-data-protection.md) (необязательно, профили защиты).

Что это значит:
- Весь Lua выполняется в одной виртуальной машине, поэтому качество песочницы критично: урезанное окружение процессов, запрет опасных функций (`getfenv`, `debug`, метатаблица строк, загрузка произвольного байткода). Это отдельная задача проекта.
- Режим восстановления (чистый CraftOS) физически обойти нельзя; вход в него защищаем паролем админа.
- Код с носителей никогда не запускается сам.

## Пользователи и вход

- Экран входа как в Windows: плитки пользователей и ввод пароля. Автовход, учётная запись "Гость" (временный дом), блокировка экрана, быстрая смена пользователя (отдельные сессии).
- Пароль хранится хэшем с солью (SHA-256 на чистом Lua; число итераций подобрать **(измерить)**), в `sys/sec/shadow.lock`. Список админов в `sudoers.lock`.
- Роли: `system`, `admin`, `user`, `guest` и свои группы.
- **Повышение прав** как sudo/UAC: диалог с паролем рисует только ядро поверх всего.

## Права файлов

Метаданных у файлов в CC нет, поэтому права задаются **правилами по префиксу пути** в конфиге (наследуются вглубь, более конкретный путь побеждает). Владелец определяется местом (всё в `users/ivan` принадлежит `ivan`). Права: чтение, запись, выполнение, список. При переносе файла права меняются на права новой ветки.

```json5
{ path: "/cubeos/sys/**",            allow: { system: "rwx", "*": "rx" } },
{ path: "/cubeos/sys/sec/**",        allow: { system: "rw" } },
{ path: "/cubeos/users/$user/**",    allow: { $user: "rwx" } },
{ path: "/cubeos/users/*/public/**", allow: { "*": "r" } },
```

## Разрешения приложений

Два слоя, итог это пересечение: права пользователя на файл и разрешения приложения.

```json5
permissions: {
  need: ["fs.appdata", "gfx"],   // без них не запустится
  want: ["net.http"],            // можно отключить галочкой
}
```

- В окне установки и в настройках у каждого разрешения галочка. `need` отключить нельзя, `want` можно; приложение обязано жить без него.
- Режимы: "разрешить всегда", "спрашивать каждый раз", "запретить".
- Сужение: `fs.read:$docs` (папка вместо "все файлы").

## Возможности (caps)

`caps` в манифесте:
- `need`: обязательно; `want`: используется, если есть.
- `compat`: проверено вместе с этим, только информация (значок в магазине), на запуск не влияет.
- `conflicts`: ломается вместе с этим; установка блокируется или предупреждает.

Определение возможности в `sys/cfg/caps.conf` (**по методам, не по типу**):

```json5
"chat.send": { periph: "chatBox", methods: ["sendMessage"] },
"inv.read":  { periph: "inventory", methods: ["list", "getItemDetail"] },
```

`mod:<modid>` это синоним, разворачивается через `sys/cfg/mods.conf` (мод в возможности). Неизвестный мод помечается "не проверить".

`need` проверяется в момент использования функции; установка не блокируется (периферия может быть подключена позже), выводится предупреждение.
